# 品牌与专业页面模板

## 品牌先于组件

输入 Logo 不足以决定品牌战略；结合产品、客户和竞争环境形成 3–5 个品牌关键词，并写明这是设计建议。保留用户已有定位。记录 Logo 比例、深浅背景、最小可辨尺寸、建议保护区；不把猜测网格称作原始 Logo 工程图。

`DESIGN.md` 应包含：采购受众、核心任务、品牌关键词、一句话定位、可信差异、语气、字体及许可、色板与对比度、图像策略、容器/字阶/间距、组件状态、移动端规则和一个具有品牌辨识度的版式特征。Logo 色可保留为品牌色；按钮文字对比不合格时另选语义交互色。

用 CSS 变量或项目既有 token 体系即可；多工具共享时再增加 DTCG 格式，不声称任意 JSON 自动符合规范。字体按语言覆盖、加载成本、品牌要求选择，不绝对禁止系统字体。行业配色只是设计参考，不是心理学结论。

## 四种采购版式

| 版式 | 首屏与主内容 | 适用场景 | 交互重点 |
|---|---|---|---|
| 工程选型 | 产品/工况入口 + 参数表 + 技术图纸 + 工程咨询 | 机械、五金、电子、电气、汽配 | 筛选、比较、资料版本、图纸询价 |
| 材料与空间 | 场景和材质细节 + 规格 + 安装节点 + 样品 | 建材、卫浴、家具 | 尺寸/表面选择、样板请求、安装下载 |
| OEM/ODM 项目 | 产品系列 + 定制选项 + 打样流程 + 包装/QC | 卫生用品、服装、鞋、箱包、包装、美妆 | 需求简报、选型、打样咨询 |
| 证据与应用 | 用途/适用边界 + 技术数据 + 文件及批次 + 咨询 | 医疗、食品、化工、部分能源 | 文件筛选、证据范围、市场条件 |

这些是组合规则而非四个固定皮肤。机械站的部件剖面、服装站的面料/工艺细节、建材站的节点/样板、电子站的数据手册都应成为真实内容组件。

## 统一页面 brief

每页先写：买家角色；要完成的决策；主要搜索意图；URL/语言；title/description/H1；内容顺序；claim_ids；素材；主 CTA 与次 CTA；相关链接；结构化数据；移动端行为；缺口；验收。文字自然，不强求标题长度或固定词数。

## 10 类页面模板

### 1. 首页 Home

结构：公司做什么/服务谁 → 行业产品/应用入口 → 可证明的选择理由 → 工作方式 → 有来源的质量证据 → 技术内容入口 → 明确询盘。

首屏主标题公式：`[真实产品/服务] for [目标应用或买家]`；副文解释可证能力和下一步。身份未知时不使用 manufacturer/factory。无认证/案例时以选型与合作流程支撑信任，不能用假数字或假客户 Logo 填空。

主 CTA 指向具体动作（Discuss Your Requirements / Request a Sample 等，服务本身需可提供）；次 CTA 看产品或规格。避免所有栏目全是 Learn More。

### 2. 产品分类 Category

结构：适用范围 → 有意义的产品分组 → 规格差异表 → 如何选择 → 证据/FAQ → 询盘。筛选字段来自行业配置及真实数据，不显示全空过滤器。

优先服务型号/材料/应用筛选，不把每个筛选组合自动建为索引页面。只对具有独立采购意图和足够内容的分类页建立可索引 URL。

### 3. 产品详情 Product

结构：正式名称/型号/用途 → 真实图片 → 核心规格表（值、单位、条件）→ 材料与结构 → 选项/定制范围 → 测试及适用范围 → 图纸/文件 → 包装/商务条件 → 同类对比 → RFQ。

规格来源与型号绑定，派生单位写明换算/舍入；不把最大值当持续工况。不确定价格就询价，不写 $0、虚构库存或默认保修。没有真实型号则先做分类页，而非伪造若干专业型号。

### 4. 应用/解决方案 Solution

结构：使用条件与任务 → 选型约束 → 可供产品组合 → 适用/不适用边界 → 工程或操作说明 → 对应证据 → 项目简报 CTA。

没有客户项目仍可发布有来源的应用指南，但不能称“客户成功案例”。不得批量复制相同内容只更换国家名。

### 5. OEM/ODM 与定制

结构：可定制维度 → 客户提供内容 → 设计/评估 → 样品与确认 → 生产/检验 → 包装交付 → 项目需求表。每步的实际责任、费用、交期按公司资料填写，未知则写需按项目确认；不保证免费设计、开模或寄样。

### 6. 制造与质量

结构：自有/协作能力边界 → 实拍工艺链 → 质检环节 → 检测方法和报告 → 追溯机制 → 文件咨询。贸易商改为供应商管理和质量协调，不展示虚构自有工厂。

证书展示包含主体、证号、范围、有效期和适用产品；只展示获准的扫描件或核验链接。标准编号不能自动变成达标声明。

### 7. About / 企业与联系

结构：正式身份 → 品牌与公司关系 → 真实业务范围 → 有资料支持的历程/团队 → 合作方式 → 联系入口。没有年份/人物资料则不编年表或创始人故事。

联系信息须精确；手机号/WhatsApp/email 不从竞品/模板继承。附时区与服务语言时同样核对。地图与地址按真实来源，不猜经纬度。

### 8. 技术资源 / FAQ / 下载中心

结构：按采购任务分类 → 原创选型指南 → 参数/工艺解释 → 适用性对比 → 公共文件 → 相关产品。每文写清实际作者/审核角色、材料来源、更新时间与适用范围；没有作者资料可使用公司编辑主体，不编工程师。

FAQ 回答真实买家问题；可用自然长度的直答+条件+证据，不固定 100–150 词。下载必须真实存在且公开获准，文件内容与网页版本一致。

### 9. 案例 / 项目

结构：背景与约束 → 选型理由 → 实施/合作范围 → 有证据结果 → 局限 → 相似需求 CTA。无授权实名时用获准匿名稿；无案例就隐藏案例栏目。数据必须交代基线、样本、时间和指标口径。

### 10. RFQ / 样品 / 项目咨询

第一步通常询问姓名、邮箱、产品/需求；公司、国家、数量及行业技术字段按业务必要性渐进展示。允许不知道型号的买家描述需求。避免只接受企业邮箱而误伤真实小买家。

提交前清楚说明资料用途与下一步；成功状态依赖服务端接收结果。失败保留输入，有重试与获准的备用联系方式。不使用前端 setTimeout 假成功。上传仅在后端验证类型/大小、私有存储和权限俱备时开放，不将图纸公开到 static 目录。

隐私与服务条款按实际数据流、接收方与目的市场配置；未经核验的法律模板不能标为合规保证。落地具体条款时查当前官方来源，必要的法律判断交给负责人员。

## 技术选择

先用现有网站技术栈。新内容型 B2B 站优先静态 HTML 或轻量静态生成；例如 Astro 可用于内容与局部交互，不强制替换 WordPress、现有 React/Next 或用户指定 CMS。只在编辑、产品数据规模或客户流程有实际需求时增加 CMS、搜索服务、账户或数据库。

保留同一组件的默认/焦点/禁用/加载/错误/成功状态。产品图设置尺寸和响应式版本，首屏主图勿懒加载；非首屏图片按需加载；避免自动播放视频拖慢采购信息。移动端规格表可横滑但应有可感知提示，操作按钮不遮挡正文或表单。

## 网站之外的品牌资产

完整品牌出海交付可从同一已批准内容派生：品牌手册、公司一页纸、产品目录、能力介绍 PPT 大纲、邮件签名、LinkedIn 资料与封面、展会落地页与二维码素材、图片/视频拍摄 brief。根据用户范围实际生成文件；不要每站强制生成全部线下导视和应用商店图标。

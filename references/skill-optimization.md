# 通用 Skill 优化与蒸馏指南 (Universal Skill Optimization & Distillation Guide)

> 沉淀自 `Anthropic Skill Creator`、`Hugging Face Skills`、`renwork-smart-skills-creator` 与真实跨领域技能优化实践。  
> 通用原则：**理解任务 → 诊断缺口 → 寻找专业方法 → 学习有效机制 → 适配创造 → 对照验证 → 沉淀经验。**

---

## 1. 能力定位与两层诊断模型

当用户要求优化自身或其他领域 Skill 时，禁止盲目“扩充字数”、“添加虚假专家人设”或“强加不相关的外贸/SEO 规则”。必须基于使用者真实任务进行两层精准诊断：

### 1.1 两层诊断矩阵
1. **通用维度 (Universal Dimensions)**：
   - **需求理解 (Intent Comprehension)**：是否分清核心目标、前置条件与不该做的事？
   - **工作流程 (Workflow Hygiene)**：是否有清晰的顺序步骤与决策分支，还是大段混乱提示词？
   - **证据质量 (Evidence Rigor)**：是否区分事实、假设与推断？有无来源追溯？
   - **工具使用 (Tool Protocol)**：脚本与命令是否健壮（参数校验、路径越界防护、失败安全退出）？
   - **输出质量 (Output Standards)**：产物是否具体、可运行、可交付，而非止步于方案名单？
   - **验证机制 (Verification Gates)**：是否有确定性测试脚本与行为对比基准？
   - **维护与成本 (Maintainability)**：是否依赖过多脆弱外部库？指令是否臃肿重复？
2. **领域维度 (Domain-Specific Dimensions)**：
   - 仅根据目标 Skill 的实际任务动态注入：
     - 若为出海建站/营销 Skill：注入买家研究、SEO/GEO、国际关税、视觉导演；
     - 若为数据分析/清洗 Skill：注入数据模式校验、缺失值处理、SQL/Python 算力优化，严禁附加 SEO 或审美要求；
     - 若为文档处理 Skill：注入排版防截断、编码格式、样式令牌。

## 2. 从 GitHub 与 Hugging Face 发现专业资源

### 2.1 检索与甄别原则
先查本机已有技能，再针对诊断出的具体缺口展开外部检索：
1. **GitHub 检索规范**：
   - 检索任务术语、专业标准、`SKILL.md` 和自动化评测仓库；
   - 必须进入作者源仓库核验：真实文件结构、最近提交 Commit SHA、开源许可协议 (MIT/Apache 等)、实际依赖和可用示例；
   - **反虚假自述原则**：Star 数量、作者头衔、夸张宣传词（如“世界最强”）不能单独作为有效证据。
2. **Hugging Face 检索规范**：
   - 检索适用于目标任务的 Skills、开源数据集、评测基准 (Benchmarks) 与轻量 Demo；
   - **任务边界隔离**：严禁把 Hugging Face 上的数据集（如 Design2Code / Pattern2Code）或纯模型权重伪称为“已经封装调用成功的 Agent Skill”。数据集提供评测思路，模型提供潜在算力，Skill 才是端到端工作流。
3. **候选来源登记格式**：
   - 解决的具体缺口；
   - 官方地址、Commit 版本与开源许可；
   - 实际阅读深度（“完整精读”、“部分阅读”、“仅看 README”必须明确标明）；
   - 提炼出的有效机制、适用条件与环境限制。

## 3. 六步机制蒸馏链 (Distillation Chain)

每项融合规则严禁生搬硬套，必须按照统一的六步链进行推导与记录：

```text
来源观察 (Source Observation)
    ↓
有效机制 (Effective Mechanism)
    ↓
适用条件 (Prerequisite Conditions)
    ↓
目标 Skill 的适配 (Adaptation to Target)
    ↓
产物具体变化 (Concrete Changes in Output)
    ↓
验证证据 (Verification Evidence)
```

### 3.1 六项实战提炼技巧
1. **对照学习 (Comparative Learning)**：对比同领域优秀实现与薄弱实现，找出导致结果质量差异的决定性步骤；
2. **反事实或删减检查 (Counterfactual Pruning)**：假想删除某条复杂规则或某段长提示词，若对最终输出质量和错误率无影响，坚决删减，维持高信噪比；
3. **跨领域机制迁移 (Cross-Domain Analogy)**：将成熟领域的优秀逻辑（如软件测试的测试金字塔、排版系统的栅格数学）迁移到新任务，重塑术语与数据契约；
4. **分离共享原则与条件分支**：当多个来源存在冲突时，将底层原则（如“证据至上”）作为共享底座，将分歧点（如“静态单页 vs SSR 架构”）转为显式条件分支；
5. **从失败与纠错中固化规则 (Failure-Driven Distillation)**：用户指正过的错误、代码抛出的异常，必须转化为不可违反的负面约束（Negative Constraints）；
6. **冗余清洗**：彻底清理重复陈述、失效依赖、无来源的硬编码数字与“假大空专家角色扮演”。

## 4. 验证、修正与经验分类 (Verification & Provenance)

### 4.1 结构检查与行为验证分离
1. **静态结构检查**：检查语法正确性、必填文件是否存在、外部依赖是否完整；
2. **实际行为验证**：使用相同输入和运行环境，并列运行优化前后的 Skill，对照产物的完成度、代码健壮性与边界覆盖率。

### 4.2 经验三态分类 (Three Confidence States)
所有写入 Skill 或优化报告的经验，必须明确标注其状态，严禁模糊混淆：
- **已验证 (Verified)**：具备实际执行日志、通过自动化测试或有真实用户回执支撑；
- **推导规则 (Inferred Rules)**：由已验证机制合乎逻辑地推导出，明确注明了适用范围与前提假设；
- **待试验 (Hypothetical / Experimental)**：新提出或未经运行验证的外部新方法，明确标记为“待测试”，不伪装为成功经验。

## 5. 四类典型验收场景 (Scenario Testing Matrix)

在优化 Skill 时，使用以下四类场景评估优化质量：

| 验收场景 | 场景特征与测试重点 | 合格验收标准 |
| :--- | :--- | :--- |
| **场景 1：网站与营销 Skill** | 优化建站、着陆页、SEO/GEO 相关技能 | 融合买家洞察、视觉系统、装柜测算与搜索引擎端点，同时保留事实与视觉边界 |
| **场景 2：非网站/数据处理 Skill** | 优化数据清洗、脚本爬取、日志分析等技能 | 严禁强加任何 SEO、关税或审美规则，聚焦算法复杂度、内存占用、容错与类型安全 |
| **场景 3：不适用的外部来源识别** | 遇到宣传过度、许可冲突或环境不可用的候选仓库 | 能清晰给出剔除理由，记录替代方案，绝不盲目合入高风险代码 |
| **场景 4：证据不足的经历识别** | 用户提出口头猜测或缺乏上下文的设想 | 明确标记为“待试验假设”，设计低成本验证方式，不把建议当作已验证事实 |
